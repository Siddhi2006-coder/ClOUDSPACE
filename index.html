// CASE STUDY 03 • IMPLEMENTATION

CLOUDSCAPE — Cloud Delivery Architecture

Educational cloud hosting exploring S3, CloudFront CDN, private storage, and HTTPS.

AWS S3 Amazon CloudFront Origin Access Control HTTPS / TLS 1.3

01 Problem

Traditional web applications frequently rely on active virtual machine origins (such as compute instances running web server software) to serve static front-end assets. This introduces unnecessary attack surfaces, operating system patch overhead, unpredictable origin load spikes, and higher latency for geographically distributed audiences.

02 Approach

Architected an educational zero-origin runtime static delivery pipeline. The site assets (clean HTML5, modular CSS3, and vanilla JavaScript) reside in a private object storage bucket with all direct public internet access blocked. Global content distribution and TLS 1.3 termination are handled entirely at edge locations through a content delivery network (CDN).

03 Architecture or Workflow

A
Private Origin Storage (Amazon S3)

Static assets are staged in an Amazon S3 bucket with "Block Public Access" fully enabled. The origin holds zero compute runtimes or public IP endpoints.

B
Origin Access Control (OAC)

Bucket access is restricted exclusively to the designated CloudFront distribution principal using AWS SigV4 request signing policies.

C
Edge Distribution & TLS (Amazon CloudFront)

CloudFront terminates HTTPS using custom TLS certificates, enforces HTTP-to-HTTPS redirects, and caches content at Point of Presence (PoP) edge servers worldwide.

04 Current Status

Active Implementation: The architecture serves as the target deployment and delivery model for this portfolio website. The codebase is maintained with zero external dependencies, making it directly deployable as static artifacts to AWS or any compliant object storage + CDN provider.

DEPLOYMENT FOUNDATION: Active hosting architecture for this CLOUDSCAPE portfolio.

User's Browser (Client Endpoint)

STAGE 01 • INITIATION

Purpose

Initiates an HTTPS request for a static resource such as index.html, CSS, JavaScript, or an image.

What Happens at this Stage

The visitor navigates to the portfolio domain. The browser queries public DNS resolvers to resolve CloudFront Anycast IP addresses, establishes a TCP three-way handshake, negotiates TLS 1.3 parameters, and emits an HTTP GET request with standard client headers (e.g., User-Agent, Accept, Accept-Encoding, If-None-Match).

Security Considerations

Modern browsers enforce HTTP Strict Transport Security (HSTS), Content Security Policy (CSP), and Cross-Origin Resource Sharing (CORS). Origin credentials or AWS IAM secret keys are never present on the client.

What the Next Stage Receives

An encrypted TLS byte stream encapsulating the HTTP GET request directed at port 443 of the nearest CloudFront Point of Presence (PoP).

// SPECIFICATION & HARDENING

Security & Engineering Considerations

Architectural design patterns for zero-origin static website hosting on AWS.

01 DATA IN TRANSIT

HTTPS & TLS 1.3 Encryption

HTTPS protects data in transit by encrypting requests and responses between the visitor and the CloudFront edge, preventing eavesdropping and packet modification.

02 ORIGIN SHIELDING

Origin Access Control (OAC)

CloudFront OAC restricts access to the S3 origin using AWS SigV4 request signing, superseding legacy OAI and ensuring objects cannot be accessed via direct S3 URLs.

03 BUCKET HARDENING

S3 Block Public Access

All four S3 Block Public Access settings should remain strictly enabled, blocking public ACLs and policies from ever exposing the bucket to direct public requests.

04 ACCESS CONTROL

Least-Privilege Bucket Policies

The S3 bucket policy permits s3:GetObject strictly to cloudfront.amazonaws.com, scoped to the specific distribution ARN using aws:SourceArn.

05 FRESHNESS & TTL

Cache Policies & Invalidations

Configured cache policies govern edge TTLs. Targeted invalidations (e.g., /index.html) immediately purge stale assets across all global PoPs upon deployment.

06 OBSERVABILITY

CloudFront Access Logging

Standard access logging streams detailed edge request records to a dedicated S3 log bucket for forensic analysis, latency tracking, and troubleshooting when configured.

ARCHITECTURAL REFERENCE NOTE

This lab presents recommended best practices for AWS cloud hosting. Configuration items describe the intended design pattern and educational model; no live AWS infrastructure is connected or billed by this static demonstration.

Documented Teaching Baseline

To guarantee repeatable calculations, this model applies deterministic arithmetic rather than randomized outputs:

  • Effective Throughput: Fixed baseline throughput of 20 Mbps (20,000 kbps).
  • Processing Overhead: 5 ms for edge PoP caching layer; 25 ms for private S3 origin retrieval.
  • Transfer Time Formula: (Asset Size in kilobits ÷ 20,000 kbps) × 1,000 ms. (Treating 1 MB = 1,000 KB).
  • Edge Cache Hit: Network Latency + Edge Overhead (5ms) + Transfer Time. (Zero S3 origin fetch).
  • Origin Fetch (Miss): (Network Latency × 2) + Origin Overhead (25ms) + Transfer Time. (Origin request required).
  • Expected Mixed Delivery: (Cache-Hit Probability × Edge Estimate) + (Cache-Miss Probability × Origin Estimate).

EDUCATIONAL FIELD NOTES • PEER REVIEWABLE
01
CACHE DYNAMICS • EDGE TERMINATION

What Actually Happens on a CDN Cache Hit?

Unpacking the exact sequence of events when an edge Point of Presence serves a cached static asset without contacting the S3 origin.

READ ARTICLE

When a client browser requests a static web asset, the goal of a Content Delivery Network (CDN) like Amazon CloudFront is to fulfill that request at the edge of the internet. A cache hit represents the most efficient execution path in cloud delivery, entirely eliminating origin load and minimizing end-user latency.

01
Anycast DNS Resolution & Local Handshake

The client's DNS query resolves to the nearest Point of Presence (PoP) IP address. TCP and TLS handshakes terminate within single-digit milliseconds of the client, establishing an optimized edge session.

02
Deterministic Cache Key Lookup

CloudFront computes a cache key using the normalized request URI, query parameters, and allowed headers. It inspects local L1 edge RAM and L2 SSD storage tiers to determine whether a valid object copy resides in memory.

03
Zero Origin Fetch & Immediate Response

Because the cached object has not exceeded its configured Time-to-Live (TTL), CloudFront streams the asset directly back with HTTP 200 OK and response header X-Cache: Hit from cloudfront. Zero network packets travel to the Amazon S3 origin.

04
Expiration Controls & Invalidation

Freshness is governed by Cache-Control max-age headers. If content must change ahead of scheduled TTL expiration, administrators dispatch a CloudFront cache invalidation to purge stale paths across all global PoPs.

KEY TAKEAWAY

A CDN cache hit completely terminates the request lifecycle at the edge perimeter. It eliminates origin egress bandwidth, protects object storage from traffic spikes, and provides predictable sub-50ms response durations.

02
ORIGIN HARDENING • AWS OAC

Why Keep an S3 Origin Private?

Examining why static website storage buckets must remain private behind CloudFront Origin Access Control rather than exposed directly to the public web.

READ ARTICLE

A frequent vulnerability in novice cloud hosting is enabling S3 Static Website Hosting with public read permissions. In a hardened production architecture, object storage should operate strictly as an isolated, private origin accessed exclusively through a designated CDN distribution.

01
Origin Access Control (OAC) with SigV4

CloudFront OAC signs all origin-bound REST requests with AWS Signature Version 4 (SigV4). S3 verifies this cryptographic signature, confirming that each request originated genuinely from the authorized CloudFront service principal.

02
S3 Block Public Access (BPA) Enforcement

Maintaining all four S3 Block Public Access settings enabled ensures that accidental ACL changes or permissive bucket policy edits cannot inadvertently expose private assets to internet crawlers.

03
Scoped Bucket Policy Conditions

The bucket policy restricts s3:GetObject actions strictly using Condition: { "StringEquals": { "AWS:SourceArn": "arn:aws:cloudfront::ACCOUNT_ID:distribution/DISTRIBUTION_ID" } }, blocking access from any other AWS account or distribution.

04
Preventing Edge Bypass & Egress Surges

If S3 were left public, external entities could bypass CloudFront caching, WAF rules, and rate limits, hitting S3 directly and triggering billable origin data transfer charges.

05
REST Origin vs. Website Endpoint Distinction

OAC SigV4 request signing works exclusively with standard S3 REST origins. S3 static website endpoints do not support authenticated OAC and require public access, making the REST endpoint the secure industry standard.

KEY TAKEAWAY

Restricting the S3 bucket to CloudFront OAC establishes defense-in-depth: it prevents perimeter bypass, eliminates unmetered direct egress charges, and guarantees that every incoming byte adheres to your configured TLS and caching policies.

03
TRANSPORT SECURITY • TLS 1.3

HTTPS Is More Than a Padlock

Exploring confidentiality in transit, message integrity validation, endpoint authentication, and the fundamental boundaries of transport security.

READ ARTICLE

Modern browsers display a security padlock icon when a site is served over HTTPS. While this indicates an encrypted connection, true transport security provides three distinct cryptographic guarantees that underpin modern internet trust.

01
Data Confidentiality (Encryption in Transit)

Symmetric ciphers negotiated via TLS 1.3 (such as AES-GCM or ChaCha20-Poly1305) encrypt all HTTP headers, URLs, and payloads, rendering intercepted network packets unreadable to eavesdroppers on public networks.

02
Cryptographic Data Integrity

Every TLS packet includes an authenticated message check (MAC). If an active attacker or rogue proxy attempts to modify HTML, inject advertising scripts, or alter JavaScript bundles in flight, the browser detects MAC mismatch and terminates the connection.

03
Endpoint Authentication & Trust Chains

Digital certificates issued by trusted Certificate Authorities prove domain ownership. They verify that the user's browser is communicating with the legitimate CloudFront endpoint rather than an adversary spoofing DNS records.

04
Strict Transport Security (HSTS)

Deploying the Strict-Transport-Security header instructs browsers to communicate with the domain exclusively over HTTPS for a specified duration, closing the plaintext redirect window against SSL-stripping attacks.

05
Security Scope & Architectural Limitations

HTTPS secures data *in flight*, but does not guard against client-side script vulnerabilities (XSS), insecure third-party packages, or misconfigured cloud permissions on the origin. Transport security is necessary, but not sufficient on its own.

KEY TAKEAWAY

HTTPS provides essential cryptographic guarantees of confidentiality, message integrity, and endpoint authenticity. However, it must be paired with least-privilege cloud IAM, strict Content Security Policies, and disciplined engineering practices.
